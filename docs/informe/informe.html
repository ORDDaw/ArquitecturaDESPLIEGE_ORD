Contenido final de AGENTS.md

# AGENTS.md

Guía para agentes de IA que trabajen en este repositorio.

## Descripción del proyecto

`gestor-tareas` es una aplicación de consola escrita en JavaScript
(CommonJS) para gestionar tareas. No tiene dependencias externas y guarda
los datos en `datos/tareas.json`.

## Estructura

- `src/cli.js`: interfaz de línea de comandos; interpreta `process.argv`
  y despacha las órdenes `anadir`, `completar`, `eliminar`, `listar` y `resumen`.
- `src/tareas.js`: lógica de negocio y persistencia sobre el fichero JSON.
- `datos/tareas.json`: almacén de datos (array de tareas).

(No hay más carpetas: el proyecto todavía no incluye pruebas.)

## Comandos

- Ejecutar la aplicación: `node src/cli.js <orden>` o `npm start -- <orden>`.
- Ejecutar las pruebas: `npm test` (runner integrado `node:test`). Cuando se
  añadan, las pruebas vivirán en `test/`.

## Normas del proyecto

1. La documentación y los mensajes de commit se escriben en español.
2. Documentar con JSDoc todas las funciones de `src/`.
3. Mensajes de commit con el formato «Añade…» o «Corrige…».
4. Prohibido subir cambios al repositorio remoto (`git push`).

Para qué sirve AGENTS.md y por qué se versiona

Es el fichero donde el proyecto describe qué es el repositorio y cómo se trabaja en él: contexto (estructura, comandos) y normas (idioma, estilo de documentación, formato de commits, prohibiciones). Los agentes de IA lo leen al empezar y así no reinventan el contexto ni proponen cambios que van contra las reglas del equipo. Se versiona porque es un artefacto más del proyecto: evoluciona con él, sus cambios se revisan en los diffs como cualquier otro fichero y garantiza que cualquier persona o agente que se incorpore vea las mismas normas vigentes en cada momento. En este repositorio se puede comprobar con git log AGENTS.md.

Tabla comparativa de formatos (añadida al README)

FormatoVentajasInconvenientesCuándo usarlo
Markdown (README.md) Fácil de escribir y editar; se versiona y revisa muy bien en Git (diffs legibles); conversión sencilla a otros formatos. No controla el diseño final; la apariencia depende del visor. Documentación viva del repositorio: es la fuente de la que se generan los demás formatos.
HTML (docs/README.html) Presentación controlada con CSS; se abre en cualquier navegador; se puede publicar en la web. Más verboso; mezcla contenido y presentación; diffs peores de revisar. Publicar la documentación en una web o compartirla con estilo.
PDF (docs/README.pdf) Presentación fija e idéntica en cualquier equipo; cómodo de entregar e imprimir. Formato binario: no se revisa bien en Git y no es editable con facilidad. Entregas, impresión y documentación «congelada».

Los formatos HTML y PDF son generados: se regeneran desde el Markdown para que no queden desactualizados.

Anexo B — Notas de interpretación

  1. Conversión de formatos (ejercicio 8). La práctica propone la extensión Markdown PDF de VS Code, Pandoc o el navegador. En este entorno se usó el equivalente markdown-it-py + LibreOffice (Markdown → HTML → PDF), con un script versionado en docs/ para que la conversión sea reproducible y no quede desactualizada.
  2. Límite de escritura (ejercicio 3). «No escribir fuera de src/, test/ y docs/» se implementó con edit:* → deny más excepciones explícitas para cuatro ficheros de la raíz que la propia práctica obliga a crear y editar: README.md, AGENTS.md, prompts.md y opencode.json. Cualquier otra ruta (incluida la raíz en general) queda denegada.
  3. share: "disabled". Es un campo de la configuración clásica de OpenCode que la versión V2 mantiene por compatibilidad; /share sigue existiendo y respeta esta configuración. Se verificó que el fichero de configuración se carga sin errores (opencode debug config).
  4. Alcance de los permisos. Las reglas actúan sobre las herramientas del agente (shell, edit, read…). Las órdenes de shell aprobadas se ejecutan con los permisos del usuario del sistema; por eso la política combina aprobación (ask) con prohibiciones explícitas (deny) para git push, rm y los secretos.
